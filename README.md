# TradingAggregator
Высокопроизводительный сервер агрегации биржевых котировок в реальном времени. Система спроектирована для работы под интенсивной нагрузкой (100k+ TPS) с учетом сетевых сбоев, частичной деградации инфраструктуры и строгих ограничений на аллокации памяти.

## Быстрый запуск

1. Убедитесь, что у вас установлен Docker и Docker Compose.
2. Выполните команду в корне проекта:
   ```bash
   docker-compose up --build
Сервисы поднимутся автоматически.Проверка HealthChecks: http://localhost:5000/health/live и http://localhost:5000/health/readyМетрики Prometheus: http://localhost:5000/metrics Архитектура и Инженерные решения (Trade-offs)1. Модель ДедупликацииПодход: Lock-free скользящее окно (Sliding Window) на базе ConcurrentDictionary и ConcurrentQueue.Ключ дедупликации: Композит из (Source, TickerId, TimestampMs, Price, Volume). Для минимизации коллизий строк тикеров (String Hashing) используется предварительный маппинг строк в строгие уникальные int TickerId через алгоритм FNV-1a.Обоснование: Поиск за $O(1)$ и отсутствие блокировок (Monitor/lock) позволяет проверять сотни тысяч тиков в секунду конкурентно из разных потоков WebSocket-адаптеров. Жесткое ограничение входящего буфера (128 байт) защищает от переполнения Large Object Heap (LOH).2. Запись в базу данных (Bulk Upsert & Temp Tables)Проблема: Поштучная вставка (INSERT) или классический UNNEST не выдержат целевой нагрузки. Низкоуровневый потоковый протокол COPY BINARY невероятно быстр, но не поддерживает ON CONFLICT DO NOTHING, что критично при деплое (Rolling Update), когда старый и новый Pod могут вычитать и отправить одни и те же данные.Решение: паттерн Temp Staging Table + Bulk Upsert.Создается TEMP TABLE IF NOT EXISTS ... ON COMMIT DELETE ROWS (для защиты системных каталогов PostgreSQL от Catalog Bloat).Данные бинарно проливаются во временную таблицу.Выполняется атомарный INSERT INTO ... SELECT ... ON CONFLICT DO NOTHING.Итог: Максимальная пропускная способность PostgreSQL с полной гарантией идемпотентности и отсутствием дубликатов.3. Backpressure и управление памятьюДанные передаются от сокетов к воркеру через System.Threading.Channels.Channel.Выбран режим BoundedChannelFullMode.Wait. Если БД замедляется, канал заполняется, и PublishAsync честно блокирует потоки-писатели (адаптеры). TCP окно (Receive Window) сжимается, заставляя операционную систему и биржу приостановить отправку пакетов (Zero Window). Это защищает систему от OutOfMemoryException.Парсинг JSON осуществляется через Utf8JsonReader и System.IO.Pipelines напрямую из unmanaged памяти (Zero-Allocation).4. Поведение при ошибкахОбрывы сокетов: Обрабатываются через Polly с бесконечным ретраем и экспоненциальным бэкоффом. «Зависшие» (Half-Open) сокеты выявляются через CancellationTokenSource.CancelAfter на операциях чтения.Сбои БД: Обрабатываются отдельным пайплайном Polly. Транзиентные сбои повторяются 3 раза. Если БД лежит «намертво», воркер заблокируется на WaitToReadAsync, накапливая данные в канале с учетом Backpressure.⚠️ Известные ограничения (Технический долг)В рамках данного тестового задания была принята семантика доставки At-Most-Once (Не более одного раза) для in-memory буферов.Сценарий потери: Если Kubernetes жестко остановит процесс (OOMKilled или SIGKILL аппаратной ноды), тики, уже вычитанные из сокета, но еще не сохраненные в PostgreSQL (находящиеся в TickChannelBus или локальном буфере воркера БД), будут потеряны.Как масштабировать до At-Least-Once:Для обеспечения 100% гарантий доставки архитектуру необходимо расширить Durable-брокером (например, Apache Kafka или RabbitMQ Quorum Queues).WebSocket-клиенты будут работать как Producers, мгновенно пуша сырые данные в топики (с acks=all). In-memory шина приложения удаляется.Воркер БД станет Consumer'ом, который будет коммитить Offset в Kafka только после успешного CommitAsync транзакции в PostgreSQL.Это обеспечит гарантию доставки At-Least-Once от сети до БД и состояние Effectively-Once благодаря нашей идемпотентной вставке в PostgreSQL
