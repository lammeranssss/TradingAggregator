# Highload Trading Aggregator

Сервер агрегации и обработки данных с биржевых торгов (WebSocket) в реальном времени.

## Как запустить

Требования: Docker и Docker Compose.

1. Склонируйте репозиторий.
2. В корневой директории (где находится `docker-compose.yml`) выполните команду:
   ```bash
   docker compose up --build
   ```
3. Система автоматически поднимет:
   - PostgreSQL (порт 5432)
   - Имитаторы бирж (порт 8080 внутри Docker)
   - Агрегатор (открывает метрики на порту 5000)

**Проверка метрик:**
Перейдите по адресу [http://localhost:5000/metrics](http://localhost:5000/metrics) для просмотра Prometheus-метрик (счетчики тиков, полнота очереди, dropped-тики).

**Проверка Health Checks:**
- Liveness: [http://localhost:5000/health/live](http://localhost:5000/health/live)
- Readiness: [http://localhost:5000/health/ready](http://localhost:5000/health/ready)

## Архитектурные и инженерные решения

### 1. Сетевое взаимодействие и парсинг (Zero-Allocation)
- Для чтения из WebSocket используется `System.IO.Pipelines`. Это позволяет обрабатывать TCP-пакеты без постоянного выделения новых массивов памяти (`byte[]`).
- Парсинг JSON выполняется поверх `ReadOnlySequence<byte>` с помощью `Utf8JsonReader`. Строки (тикеры) не аллоцируются в памяти на каждый тик — используется пулинг строк (`StringPool` из CommunityToolkit.HighPerformance).

### 2. Модель дедупликации
- **Ключ дедупликации:** Уникальность определяется композитным ключом: `(ExchangeSource, TickerId, TimestampMs, Price, Volume)`.
- **Реализация:** Написан кастомный `LockFreeDeduplicator` на базе `ConcurrentDictionary` и `ConcurrentQueue`.
- **Очистка:** Воркер очистки (Timer) работает за константное время и вычищает старые записи (окно в 5 секунд), не блокируя читающие потоки.

### 3. Механизм Backpressure и Обработка потока
- Между WebSocket-клиентами и воркером базы данных находится шина на базе `System.Threading.Channels` (`BoundedChannel` на 100 000 элементов). 
- Это позволяет сглаживать микро-всплески (spikes) нагрузки. Если канал переполнен (например, БД отвечает слишком долго), канал переходит в режим `Wait` (для `PublishAsync`) или `DropOldest` (для синхронного `TryWrite`), предотвращая `OutOfMemoryException`.

### 4. Стратегия записи в БД (Batching & Upsert)
- Запись идет батчами (размер 1000 тиков или каждые 500 мс, смотря что наступит раньше).
- Для максимальной производительности вместо множества `INSERT` используется механизм **PostgreSQL `COPY BINARY`** во временную таблицу (`temp_ticks`), с последующим выполнением `ON CONFLICT DO NOTHING` при слиянии с основной таблицей.

### 5. Поведение при ошибках и сбоях
- **Обрыв сети:** Реализован бесконечный механизм Retry с экспоненциальным backoff и Jitter'ом через библиотеку `Polly`.
- **Зависшие сокеты (Half-Open):** В цикле чтения реализован таймаут ожидания (Idle Timeout = 15 сек). Если биржа молчит, TCP-соединение принудительно разрывается и инициируется переподключение.
- **Ошибки БД:** При кратковременных сбоях `Polly` делает 3 попытки записи. Если БД лежит "намертво" и попытки исчерпаны, батч отбрасывается, но **не молча**: инкрементируется явная метрика `aggregator_ticks_dropped_total`. Это осознанный компромисс между отказоустойчивостью и защитой оперативной памяти процесса от переполнения.
- **Graceful Shutdown:** При получении `SIGTERM` канал помечается как `Complete()`, новые тики отбрасываются, а `BatchProcessorWorker` получает 5 секунд на то, чтобы "слить" остатки данных (drain) в БД перед физическим завершением процесса.

## Известные ограничения (Trade-offs)
1. Строгая консистентность (Exactly-Once) не гарантируется. В угоду high-throughput производительности применен подход At-Least-Once на сетевом слое + Идемпотентность (ON CONFLICT) на уровне базы данных.
2. В текущей реализации при длительном отказе БД данные из in-memory буфера отбрасываются (фиксируется метрика `dropped_total`). Возможная архитектурная доработка для production: сброс отброшенных батчей в холодное хранилище (например, локальные WAL-файлы, AWS S3 или Kafka) для последующего recovery-процесса.
